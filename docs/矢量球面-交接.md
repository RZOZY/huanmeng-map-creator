# 交接：把地球仪改成「矢量球面」

> 本文档供**新会话**接手使用。请先完整读一遍再动代码。
> 上一轮会话已把所有贴图方案试尽并证伪，本文档记录**已验证的事实**与**明确可执行的方案**，
> 目的是让新会话**一次做对**，不再重复试错。

---

## 一、目标

地球仪视图目前用「球面 + 等距圆柱贴图」，有两个无法回避的问题：

1. **极点收敛**：地图顶边整行在球面上收敛成一个点 → 极区地形被挤成放射状花瓣
2. **经线接缝**：地图左右两端内容不同 → ±180° 处一道硬边

**目标**：改成**矢量球面** —— 不贴图，直接用地图自己的 Voronoi 多边形，按每个顶点的经纬度投到球上。
这样极点是**普通顶点**（不是收敛线），多边形本身跨过 ±180°（没有接缝），两个问题一起消失。

## 二、已验证的事实（不要重复试错）

### 2.1 贴图路线到此为止

three.js 官方论坛同一问题（[链接](https://discourse.threejs.org/t/distortion-on-applying-texture-with-plate-carree-projection-to-sphere/89562)）的原话：

> **grml**：「一般来说，把一张 2D 图片贴到球上、还想没有畸变，是**不可能的**。
> 另有一种叫 Cube Sphere 的做法（六张 cube map），已算最好，但仍有畸变。
> **如果你能想出无畸变的单图投影，去申请专利。**」

### 2.2 本项目已实测失败的方案（都已回退，勿再尝试）

| 方案 | 结果 |
|---|---|
| 极区模糊 + 极冠压平 | 极区看不清，用户否决 |
| 极点补偿小图（方位等距投影） | 太小看不清；放大后仍有花瓣，否决 |
| **Cube Sphere**（六面立方体贴图 + 归一化 Box + 方向采样着色器） | **实测拼接感更强，比单张贴图更差**（六个面之间有明显直线接缝） |
| 换完整世界高度图 | ✓ **有效但这只修数据层**，已发布 cn.12 |

**结论**：极点收敛是「把平面图贴到球上」的数学性质，**贴图方式无解**。

### 2.3 仍然有效的贴图侧改进（已发布）

- cn.12：替换了截断的 `public/heightmaps/world.png`（详见上游 issue #990）
- cn.13：`texture.anisotropy` + mipmap，改善清晰度

## 三、必须遵守的坐标换算（上次失败的主因就在这里）

**铁律：`lonT` / `latT` 是「跨度」，不是边界。** 引擎自己的定义在
[`src/utils/commonUtils.ts`](../src/utils/commonUtils.ts) 第 250、262 行：

```ts
// 地图像素 (x, y) → 经纬度
lon = mapCoordinates.lonW + (x / graphWidth) * mapCoordinates.lonT;
lat = mapCoordinates.latN - (y / graphHeight) * mapCoordinates.latT;
```

默认值（`src/data/options-model.ts`）：

```ts
coordinates: { latT: 180, latN: 90, latS: -90, lonT: 320, lonW: -160, lonE: 160 }
```

- `lonT = 320` **是经度跨度**（= `lonE - lonW = 160 - (-160) = 320`），**不是东边界**
- **上次的 bug**：写成 `lonT - lonW` 得到 **480°**，超过一整圈 → 几何体自相交 → 渲染成碎片

**经度方向的处理**：引擎的球面贴图是把地图**横向拉伸铺满整圈 360°**（见 `updateGlobeTexure` 里
`mapWidth = mapHeight * 2`）。矢量球面应照做，否则会留出空洞：

```ts
lon = -180 + ((x - minX) / spanX) * 360;   // 拉伸铺满整圈
lat = latN - ((y - minY) / spanY) * latT;  // 纬度用真实跨度
```

**球面坐标**（与现有贴图球体一致，可保证朝向相同）：

```ts
const phi = (90 - lat) * (Math.PI / 180);
const theta = (lon + 180) * (Math.PI / 180);
return [-Math.sin(phi) * Math.cos(theta), Math.cos(phi), Math.sin(phi) * Math.sin(theta)];
```

## 四、数据结构

```ts
// src/types/GridGraph.ts
grid.points[i]            // 单元 i 的中心 [x, y]
grid.cells.v[i]           // 单元 i 的顶点索引数组（多边形的环）
grid.vertices.p[j]        // 顶点 j 的坐标 [x, y]
grid.cells.h[i]           // 高度 [0,100]，20 是海平面
grid.boundary             // 地图边缘的伪点（不是真实单元）
gridToPackCellMap         // grid 单元 → pack 单元；注意它只在地形烘焙时才填充！
```

**取色的可靠做法**：不要依赖 `gridToPackCellMap`（会为空，导致整球全蓝）。
从 `pack.cells.g` 建反查表：

```ts
const packOfGrid = new Map<number, number>();
for (let i = 0; i < pack.cells.i.length; i++) {
  const gridIndex = pack.cells.g[i];
  if (gridIndex !== undefined && !packOfGrid.has(gridIndex)) packOfGrid.set(gridIndex, i);
}
const stateId = pack.cells.state[packOfGrid.get(cell)!];
const state = stateId ? pack.states[stateId] : undefined;
const biome = pack.biomes?.[pack.cells.biome[packOfGrid.get(cell)!]];
const color = state?.color ?? biome?.color ?? (isLand ? "#c8bfa8" : "#466eab");
```

## 五、上次失败的第二个原因

第二次尝试时按「顶点实际范围」归一化（`minX/maxX/minY/maxY`），结果：

- **极点出现黑洞**（最外一圈单元的中心离地图边还有半个间距，顶点没铺到边上）
- **中间裂开一道黑缝**（地图左右边缘的单元不完整、被 `corners.length < 3` 跳过）

**这一次必须先解决边界**：

1. 遍历时把 **`grid.boundary` 伪点**也纳入范围计算
2. 对 `corners.length < 3` 的单元**不要直接 continue** —— 打印出来看有多少、在哪，再决定
3. 或者反向做法：遍历 **`grid.vertices.v[j]`（每个顶点的相邻顶点）** 自己组装多边形，避免依赖 `cells.v`

## 六、推荐实施计划（分三步，每步都要验证）

### 第 1 步：只做数学验证（不碰渲染器）

写一个临时函数，把若干已知点的 (x, y) → (lon, lat) → 球面坐标算出来，
在控制台打印，与理论值逐项对比。**确认无误才进入第 2 步。**

要验的点（用默认坐标 latT=180, latN=90, latS=-90, lonT=320, lonW=-160）：

| 地图像素 | 期望经度 | 期望纬度 |
|---|---|---|
| `(0, 0)` | -180（铺满整圈后） | +90 |
| `(W, 0)` | +180 | +90 |
| `(W/2, H/2)` | 0 | 0 |
| `(0, H)` | -180 | -90 |

### 第 2 步：只出几何体，不上色

用纯色（比如统一灰色）渲染矢量球面，**截图确认**：

- 是一个完整、没有黑洞的球
- 没有裂缝
- 极点没有花瓣（顶点在那里自然汇聚，但不应有"放射状细线"）

### 第 3 步：上色

按第四节的取色方式给每个单元上色，再截图确认。

**每一步都截图确认后再进入下一步。不要一次性做完再打包。**
